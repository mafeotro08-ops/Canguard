Arquitectura CANGUARD

Sistema de Gestión de Unidades Caninas K9 — análisis de la arquitectura actual, justificación de la pila tecnológica y hoja de ruta de evolución.

Agosto 2026 mfotero@109apps.com FastAPI · Jinja2 SSR · MySQL

01 — Contexto

Resumen del Proyecto

CANGUARD es una aplicación web de gestión operativa para unidades caninas K9. Centraliza el registro de caninos, guías, programas de entrenamiento, sesiones, video-análisis con inteligencia artificial, gestión de usuarios y alertas — todo bajo un modelo multi-entidad con control de acceso por roles.

La aplicación sigue el patrón de Server-Side Rendering (SSR): el servidor Python genera HTML completo y lo entrega al navegador. No existe un frontend separado; toda la lógica de vistas vive en las plantillas Jinja2 y en el servidor FastAPI.

Estado actual: 18 plantillas HTML, ~3 200 líneas de rutas en main.py, 70+ funciones SQL en models.py, integración con OpenAI API para transcripción y análisis de video.

02 — Estructura

Arquitectura Actual

El sistema está organizado en cuatro capas funcionales que operan en cadena vertical: la solicitud HTTP entra por la capa de aplicación, se resuelve contra los datos y vuelve como HTML completamente renderizado.

Vista por Capas

Capa 1 — Presentación (Navegador del Cliente)

Jinja2 Templates · 18 archivos Bootstrap 5 CSS Custom Properties Chart.js 4.4 SweetAlert2 Bootstrap Icons Vanilla JavaScript
HTTP Request ↕ HTML Response (SSR)

Capa 2 — Aplicación (main.py + auth.py)

Llamadas Python directas a funciones

Capa 3 — Acceso a Datos (models.py + database.py)

~70 funciones SQL _query() — helper centralizado mysql-connector-python Queries parametrizadas Soft-delete (activo = 0)
TCP / MySQL Wire Protocol

Capa 4 — Base de Datos (MySQL 8.x)

MySQL 8.x ~15 tablas Multi-tenant via id_entidad Esquema manual — sin migraciones

Descripción de cada capa

Capa 1 — Presentación

Las plantillas Jinja2 heredan de layout.html, que incluye el menú lateral, los CDN de Bootstrap/Chart.js/SweetAlert2 y el polling de notificaciones. Cada página extiende los bloques content, extra_css y extra_js. No hay bundler ni transpilación: el JavaScript vive directamente en etiquetas <script> dentro de cada plantilla.

Capa 2 — Aplicación

main.py concentra todas las rutas. Cada ruta sigue el patrón guard → filtro de entidad → lógica → render: verifica sesión activa con redirigir_si_no_autenticado(), aplica el filtro multi-tenant (id_ent = None if es_super_admin else id_entidad_sesion), llama funciones de modelo y retorna un TemplateResponse con el contexto necesario.

Capa 3 — Acceso a Datos

Toda interacción con MySQL pasa por la función privada _query(sql, params, write=False) en models.py, que abre la conexión, ejecuta y la cierra. Las funciones de modelo son envoltorios SQL explícitos sin ORM. El soft-delete (activo=0) es el patrón universal para borrado lógico.

Capa 4 — Base de Datos

MySQL organiza los datos bajo el concepto de entidad (id_entidad): cada registro de canino, usuario, programa o sesión pertenece a una entidad. Los super_admin ven todo; los admin_entidad solo ven sus registros. El esquema se gestiona manualmente — no hay historial de cambios ni rollback automatizado.

Control de Acceso (RBAC)

Rol Alcance Restricciones
super_admin Global — todas las entidades Sin restricciones. Puede borrar programas, sesiones, gestionar cualquier entidad.
admin_entidad Solo su entidad No puede borrar programas ni sesiones. No accede a otras entidades.

La sesión vive en una cookie firmada con SessionMiddleware de Starlette. La inactividad se controla comparando el timestamp de la última actividad contra SESSION_LIFETIME (variable de entorno, defecto 3 600 segundos).

03 — Decisión Tecnológica

Por qué Python y FastAPI

La elección de Python con FastAPI no fue arbitraria. Tres factores del proyecto definen la decisión:

  • Integración con IA: El módulo Visión IA consume la API de OpenAI. Python domina este ecosistema — las librerías de IA (OpenAI SDK, Whisper, LangChain, etc.) tienen soporte de primera clase solo en Python. Con Node.js o PHP, esta integración habría requerido wrappers no oficiales.
  • Velocidad de prototipado: FastAPI genera documentación OpenAPI automática, valida tipos con Pydantic y no impone ORM, estructura de carpetas ni convenciones rígidas desde el primer día. Django hubiera añadido complejidad (admin panel, ORM, migrations) que el equipo no necesitaba al inicio.
  • Rendimiento async: FastAPI usa ASGI y es async-first. Su throughput en cargas I/O-bound (consultas a BD, llamadas a OpenAI) es comparable a Node.js y superior a Django/Flask en configuración equivalente.

Comparativa de frameworks

Framework Async nativo Ecosistema IA Curva inicial Docs automáticas SSR fácil
FastAPI ✓ ASGI nativo Excelente Media OpenAPI / Swagger Jinja2 integrado
Django Parcial (ASGI opt.) Bueno Alta Manual Templates propios
Flask No (sync) Bueno Baja Manual Jinja2
Express (Node.js) Event loop Limitado Media Manual EJS / Pug
Laravel (PHP) No Muy limitado Media Parcial Blade
Spring Boot (Java) Reactor / WebFlux Moderado Alta Swagger Thymeleaf
Síntesis: FastAPI ofrece la mejor combinación de desarrollo rápido, async real, ecosistema IA y documentación automática para los requisitos de CANGUARD. Django es la alternativa más cercana, pero su peso (ORM obligatorio, admin panel, convenciones estrictas) lo hace excesivo para un equipo pequeño con un dominio bien delimitado.

Lo que funciona bien de la arquitectura actual

  • El SSR con Jinja2 es simple de mantener: un cambio en la plantilla se ve inmediatamente sin rebuild ni bundler.
  • Las queries parametrizadas en _query() previenen inyección SQL de forma centralizada — no hay riesgo de concatenación de strings insegura.
  • El soft-delete universal (activo=0) preserva historia sin papeleras complejas ni referencias rotas.
  • El modelo multi-tenant via id_entidad funciona bien mientras las entidades no superen los cientos.
  • La integración con OpenAI es directa y mantenible gracias al SDK oficial de Python.

04 — Evolución

Roadmap de Mejoras

Las mejoras están ordenadas por urgencia e impacto. Las dos primeras fases eliminan deuda técnica activa que crece con cada nueva funcionalidad. Las últimas dos preparan el sistema para crecimiento real en usuarios y equipo.

Corto plazo

Modularización

Problema actual

  • main.py concentra todas las rutas (~3 200 líneas) — difícil de navegar, probar y mantener en equipo.
  • La lógica de negocio está mezclada con la lógica HTTP (validaciones, cálculos y renders en la misma función).

Qué hacer

  • Crear routers/ con un APIRouter por dominio: caninos.py, cursos.py, usuarios.py, vision.py, entidades.py, notificaciones.py.
  • Extraer lógica de negocio a services/ — cada ruta solo guarda, delega y renderiza.
  • Centralizar configuración en config.py con pydantic-settings — fallo claro si falta una variable de entorno.
  • El main.py resultante queda en <100 líneas: solo registra routers y middleware.
Mediano plazo

Persistencia Robusta

Problema actual

  • Sin versionado de esquema: los cambios de BD se aplican manualmente — sin historial, sin rollback.
  • _query() abre y cierra una conexión por llamada — ineficiente bajo carga concurrente.
  • Los diccionarios retornados por MySQL son frágiles: renombrar una columna rompe código silenciosamente.

Qué hacer

  • Introducir SQLAlchemy 2.x con modelos declarativos — tipado explícito, relaciones documentadas en código.
  • Agregar Alembic para migraciones versionadas: alembic upgrade head aplica cambios reproducibles en cualquier ambiente.
  • Configurar un connection pool explícito en el engine de SQLAlchemy (pool_size, max_overflow).
  • Mantener el soft-delete (activo=0) como mixin reutilizable en los modelos.
Mediano plazo

Calidad y Despliegue

Problema actual

  • Sin tests automatizados: cualquier refactor es un riesgo ciego. No hay forma de detectar regresiones.
  • El entorno de desarrollo no está containerizado — diferencias entre máquinas pueden romper el proyecto silenciosamente.
  • No hay pipeline CI/CD formal que bloquee código roto antes de llegar a producción.

Qué hacer

  • pytest + httpx.AsyncClient (TestClient de FastAPI) para tests de integración de rutas críticas (login, RBAC, caninos, cursos).
  • Docker + docker-compose.yml con servicios: app (FastAPI) + db (MySQL) + (futuro) redis.
  • GitHub Actions con pipeline: lint (ruff) → tests (pytest) → build image → deploy según rama.
  • Variables de entorno validadas al arranque con pydantic-settings — error explícito si falta DB_HOST, SECRET_KEY, etc.
Largo plazo

Escalabilidad

Cuándo aplica

  • El número de entidades supera las decenas y los reportes del dashboard se vuelven lentos.
  • La transcripción de videos con OpenAI bloquea el servidor varios segundos por solicitud.
  • Se necesita una app móvil o integraciones con sistemas externos (ERP, plataformas de terceros).

Qué hacer

  • Redis para caché de queries frecuentes (listas de caninos, programas) y para almacenar sesiones fuera del proceso — permite múltiples instancias del servidor.
  • Celery + Redis como broker de tareas: mover la transcripción de OpenAI a un worker en background — el usuario recibe un ID de tarea y consulta el estado de forma asíncrona.
  • Separar una API REST en /api/v1/ con respuestas JSON, para que el SSR conviva con integraciones externas o una futura app móvil sin reescribir el servidor.
  • Evaluar HTMX antes de saltar a React/Vue — permite actualizar fragmentos de HTML desde el servidor sin un SPA completo, manteniendo la simplicidad del SSR.
  • Sentry para captura de errores en producción + logs estructurados en JSON para observabilidad real.

05 — Síntesis

Conclusión

CANGUARD tiene una base técnica sólida para su estado actual. FastAPI + Jinja2 SSR es una elección bien justificada, las queries parametrizadas garantizan seguridad frente a inyección SQL, y el modelo multi-tenant funciona de forma predecible. El punto de quiebre más cercano no es el lenguaje ni el framework — es la concentración de todo el código de rutas en main.py y la ausencia de tests automáticos.

Ambos problemas son resolubles en horas de trabajo, no en semanas de reescritura. Hacerlos ahora, cuando el codebase todavía es navegable por una sola persona, cuesta mucho menos que hacerlos cuando el equipo sea mayor o la base de usuarios sea real.

Prioridad inmediata: Separar main.py en APIRouter por dominio (Fase 1) y agregar tests básicos para las rutas de autenticación y RBAC (Fase 3). Esas dos acciones eliminan los riesgos más activos sin tocar la arquitectura ni la base de datos.
